# Dimer v0.1 Finalization Plan

**Purpose:** This is the implementation handoff for completing Dimer's first release. It deliberately replaces the old assumption that every numbered phase must be completed in order.

**Release decision:** Dimer is functionally a v0.1 data-native analysis agent already. Finish the release by validating the current implementation, polishing the existing chat surface, and adding a narrow reproducibility export. Do not expand the Textual TUI or build a general production-pipeline platform.

**Progress (2026-07-15):** The deterministic baseline, described chat slash completion, and verified SQL session export are implemented. `uv run pytest -q` passes with 89 tests and `git diff --check` is clean. Deterministic CLI checks pass. Fresh sales/retail/churn live-model acceptance remains pending because no local Ollama or LM Studio server was available.

## Product Position

Dimer is a **local-first, terminal-native data agent**, not a generic coding agent with pandas added. It should understand and preserve analytical context:

- local datasets, schemas, columns, quality issues, and filters
- notebook code, comments, outputs, and execution-order caveats
- SQL/Python analysis steps and generated charts/reports
- assumptions, evidence, artifacts, and session provenance
- the path from exploratory analysis to a repeatable workflow

The defining user workflow remains:

```bash
dimer ask data/sales.csv "Why did revenue drop in March?"
```

The response must be grounded in computed evidence, state uncertainty plainly, create useful artifacts when appropriate, and make the analysis traceable.

## Why This Is the Right Finish Line

The inspiration article in `notes/Why AI Agents Struggle More With Data Science Code Than Software Engineering Code _ DataCamp.pdf` argues that data-science meaning lives in external state: datasets, intermediate outputs, assumptions, and evolving questions. Dimer already addresses much of this with profiles, notebook summaries, data-quality findings, assumptions, artifacts, sessions, and SQL lineage.

The major missing first-version bridge is **reproducibility**: turning an evidence-backed exploratory session into a runnable artifact. A narrow SQL-session export closes that gap. A richer fullscreen TUI does not.

## Current State

The living implementation/status reference is `project-context/Instructions-status.md`; the original requirements are in `project-context/Instructions.md`.

### Complete enough for v0.1

- CLI commands for initialization, profiling, context, SQL, artifacts, assumptions, sessions, trace, notebook summary, and one-shot analysis.
- Provider abstraction and local/cloud-compatible providers.
- Tool-driven agent loop with JSON fallback, validation/normalization, approvals, and final-answer sections.
- DuckDB analysis over local data, persistent Python execution, reports/charts, and artifact registration.
- Data-quality v1, session/column/SQL lineage, and read-only notebook awareness.
- Baseline ML mode with train/test split, metrics, feature importance, and post-outcome leakage exclusions.
- Scrollback `dimer chat`, which is the preferred interactive surface.

### Do not continue

- Do not add Phase 7 Textual TUI features. `dimer tui` may remain available, but it is not a release priority.
- Do not create a generic pipeline mode, scheduler, DAG system, dbt/Airflow integration, or notebook executor.
- Do not pursue AutoML, advanced charts, graph databases, or Python-variable lineage in v0.1.
- Do not refactor stable modules merely to make the architecture more elaborate.

## Release Work

Work in this order. Keep changes scoped and update `implementations.md` and `Instructions-status.md` only after a task is verified.

### 0. Establish a trustworthy baseline

The repository currently has an environment issue: the active x86_64 Python process loads arm64 compiled packages from `.venv`, so `uv run pytest -q` fails during collection with architecture errors from `numpy` and `pydantic-core`. This is not evidence of an application failure, but it blocks release validation.

1. Recreate/sync the environment for the active Python architecture.
2. Run `uv run pytest -q` successfully.
3. Run `git diff --check` and retain a clean result.
4. Check the existing worktree carefully. It contains uncommitted Phase 5, reliability, and Phase 7 code plus tests; do not discard user work.
5. Do not claim a passing test count until it has been rerun in the repaired environment.

### 1. Make `dimer chat` the polished primary UX

The current `dimer/ui/interactive.py` delegates state and slash command handling to `dimer/ui/session_controller.py`. Preserve that separation; changes to command semantics should live in `SessionController` so the REPL and retained TUI stay consistent.

#### Required outcomes

- Typing `/` in the REPL presents an interactive command menu/completion list, like modern coding-agent CLIs.
- Each completion shows a short description, not only a command token.
- Commands with arguments offer useful contextual completions where practical:
  - `/mode` -> `analysis`, `sql`, `ml`
  - `/artifacts` -> `session`, `all`
  - `/model` -> `default` at minimum
  - `/trace` -> documented forms (`all`, `session`)
- The existing commands remain supported: `/help`, `/exit`, `/context`, `/profile`, `/artifacts`, `/assumptions`, `/notebook`, `/sessions`, `/replay`, `/mode`, `/provider`, `/model`, `/trace`, `/status`.
- `/help` is concise and readable; it should complement the interactive menu, not dump noisy implementation details.
- Status remains visible but compact after a command changes mode, provider, model, dataset, notebook, or session.
- Tool progress, approvals, generated artifacts, assumptions, and failures remain easy to scan in scrollback.

#### Implementation guidance

- Use prompt_toolkit completion APIs rather than parsing terminal input manually.
- Add focused unit tests for completion candidates and descriptions, leading-whitespace slash commands, and any new status rendering.
- Do not make a new UI framework or port Textual widgets into the REPL.

### 2. Implement Phase 6 first slice: deterministic SQL session export

This is the only Phase 6 work required for v0.1. The previous design is in `project-context/phase-6-pipeline-future.md`; use it as the base but add lightweight verification.

#### User interface

```bash
dimer export [session_id]
```

- Omitted `session_id` exports the latest session.
- Chat supports `/export` and `/export <session_id>`.
- Print the created script path and any verification/schema warnings.

#### Source of truth and eligibility

- Read the saved session JSON through `dimer.storage.sessions`, not chat text.
- Export ordered, successful `run_duckdb_query` entries using recorded `arguments.query` and `arguments.data_paths`.
- Skip failed calls and duplicate-blocked calls.
- Deduplicate identical successful calls while retaining execution order for distinct queries.
- If no eligible queries exist, return a clear actionable message and do not create a fake script.

#### Generated artifact

Write one runnable Python script to `.dimer/artifacts/scripts/`, then register it through `ArtifactRegistry` as `type="script"` with the originating `session_id`.

The script must:

- use DuckDB and the same file-stem-to-table-name rules as `dimer/tools/duckdb_exec.py`
- register every required CSV/Parquet source path
- run each exported query in order and print a bounded preview
- contain a header with the session ID, original question, mode, export time, and recorded assumptions
- avoid LLM-generated cleanup or rewrites of the original SQL

#### Verification and drift warning

At export time, build a small JSON manifest next to the script or embed it as a header payload. For each source, record at least its resolved path, table name, and a schema/profile fingerprint sufficient to warn about changed columns/types later.

- Verify that the generated script is syntactically valid and that its queries execute against the current source files at export time.
- Export succeeds with a warning when a saved source no longer exists or its schema differs, only if the script can still be written and the warning makes the limitation explicit. Prefer a failed verification status over pretending the replay succeeded.
- The script itself should validate source existence and emit a clear schema-drift warning before executing queries where feasible.

This is intentionally not a data-validation framework. It is enough to make the exported analysis honest and replayable.

### 3. Run release acceptance checks

Unit tests alone are insufficient because Dimer's core value is tool-backed analytical behavior. Run these after the environment is repaired and record the actual results.

#### Deterministic checks

```bash
uv run pytest -q
uv run dimer init
uv run dimer profile examples/sales/sales.csv
uv run dimer context .
uv run dimer sql examples/sales/sales.csv "SELECT region, SUM(revenue) AS total FROM sales GROUP BY region"
uv run dimer export <session-with-successful-sql>
python .dimer/artifacts/scripts/<exported-script>.py
```

#### Chat UX checks

1. Start `dimer chat`.
2. Type `/` and verify a readable completion menu with descriptions.
3. Use `/mode ml`, `/status`, `/artifacts`, and `/trace all revenue`.
4. Profile a dataset with `/profile ...`, ask a question, and verify status/session/artifact output remains compact and legible.
5. Exercise a denied and accepted approval-required operation.

#### Agent acceptance checks

With an available local model, run and inspect evidence rather than trusting prose:

```bash
uv run dimer ask examples/sales/sales.csv "What are the most important trends?"
uv run dimer ask examples/sales/sales.csv "Why did revenue drop in March?"
uv run dimer ask examples/retail_ops "Why did revenue drop in March?"
uv run dimer ask examples/saas_churn "Train a baseline model to predict churn" --mode ml
```

Acceptance requires that the output is computation-backed, labels caveats/leakage, does not expose malformed tool JSON as findings, and produces traceable artifacts where appropriate. Local models may still stop early; document this honestly if it remains true after the reliability work.

## v0.1 Release Criteria

Dimer v0.1 is ready when all of the following are true:

- The deterministic tests pass in a compatible environment.
- `dimer chat` has discoverable slash commands with descriptions and retains its existing reliable workflows.
- A session containing successful SQL exports to a registered, runnable, verified script through CLI and chat.
- The sales/retail/churn acceptance scenarios have current recorded results, including known model limitations.
- README and project status describe only verified behavior and the actual test result.
- Current implementation changes are reviewed and committed without reverting unrelated user work.

## Explicit Post-v0.1 Work

These are valuable but must not block the release:

- Python/dataframe variable provenance and notebook kernel/state replay. This is the largest remaining gap relative to the inspiration article.
- Joined-feature ML assembly for multi-table data.
- Full notebook productionization, richer schema validation, config packs, and pipeline orchestration.
- More sophisticated charting and statistical driver search.
- Live acceptance coverage for Ollama and cloud providers.
- Further Textual TUI work, only if real users later demonstrate that chat is insufficient.

## Handoff Rules

1. Prefer the narrowest implementation that satisfies the release criteria.
2. Preserve data-context evidence and session provenance; never replace computed output with unsupported model narration.
3. Keep agent logic out of UI modules.
4. Treat `Instructions-status.md` as a living, evidence-based status record. Update it only after implementation and verification.
5. Finish at the v0.1 release criteria. Do not continue into the post-v0.1 list without an explicit request.
